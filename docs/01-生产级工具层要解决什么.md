# 01 · 生产级工具层要解决什么

> 目标：读完这一篇，你能说清楚「工具调用」为什么是 Agent 系统里最容易出事的一层，
> 以及六个机制分别在防什么。

## 0. 先建立正确的心理模型

很多人把工具想成"一个函数"。在 Agent 系统里它是三样东西：

```
工具 = 一段有副作用的代码
     + 一个不可预测的调用方（大模型）
     + 一个不保证可用的下游
```

第二条是普通后端没有的。普通后端里，**调用参数是人写的**，人写错了你看得见。
Agent 里参数是**模型生成的**，它可能：

- 传错类型（`"5"` 而不是 `5`）
- 漏必填参数
- 编一个不存在的工具名
- 传一个语义上荒谬但格式合法的值（城市名写"火星"）
- 一轮里调用 10 个工具
- 反复调同一个工具

所以工具层的职责不是"执行函数"，而是**在不可信的调用方和脆弱的下游之间做一层缓冲**。

## 1. 参数校验：不只是"检查类型"

### 1.1 为什么必须服务端真的校验

一个常见错误：给模型声明了 JSON Schema，就以为模型会遵守。

```python
# 声明了 enum 和 maximum，但函数体里不检查
{"mode": {"type": "string", "enum": ["fast", "safe"]},
 "amount": {"type": "number", "maximum": 10000}}
```

模型 95% 的时候会遵守，但那 5% 会直接写进你的数据库。
**Schema 是给模型看的建议，校验是给自己的保证。两者都要有。**

### 1.2 错误信息要带 JSON 路径

对比：

```
A: 参数校验失败
B: 参数校验失败：$.order_id: 不匹配模式 '^ORD-\d{4}$'，收到 '1234'；$.amount: 不能大于 10000，收到 99999
```

A 回灌给模型，模型只能瞎猜哪里错了，大概率再错一次。
B 直接告诉它**哪个字段、期望什么、实际收到什么** —— 模型大概率能自己改对。

这就是「错误即 prompt」：**在 Agent 系统里，错误信息不是给程序员看的日志，是给模型看的指令。**

### 1.3 类型纠偏要有底线

模型经常把 `5` 写成 `"5"`，做保守纠偏能省一轮交互。但有两条底线：

- **`True` 不能当成整数 1**。Python 里 `isinstance(True, int)` 为真，不拦就会静默出错。
- **只在无歧义时转换**。`"abc"` 转不成整数，就老老实实报错，别猜。

还有一个容易忽略的：**多余参数应该忽略而不是报错**。
模型多塞字段比漏字段常见得多，报错会让它陷入无意义的重试。

## 2. 重试：最容易做错的一层

### 2.1 重试的第一原则：搞清楚"该不该重试"

这是整个库的设计中心。看这张表：

| 失败原因 | 重试有用吗 | 为什么 |
|---|---|---|
| 参数不合法 | ❌ | 重试一百次参数还是错的 |
| 网络抖动 | ✅ | 瞬时故障，重试就好 |
| 429 限流 | ✅ | 等一会就好 |
| 超时 | ✅ | 可能是瞬时变慢 |
| 下游整体挂了 | ⚠️ | 短期没用，应该熔断 |
| 代码 bug（`TypeError`） | ❌ | 重试只会掩盖 bug |
| 非幂等写操作 | ❌ **危险** | 可能重复下单/重复扣款 |

**对一个参数错误做三次指数退避重试，是新手最常见的浪费。**
所以这个库把 `retryable` 编码进错误类型，而不是让每个调用点自己判断。

### 2.2 必须加抖动（jitter）

不带抖动的指数退避是这样的：100 个请求同时失败，然后在 1s、2s、4s 同时重试 ——
形成**重试风暴**，把刚恢复的下游再打挂一次。

```
无抖动:   1.0s  2.0s  4.0s   ← 所有请求整齐划一，峰值叠加
带抖动:   0.8~1.2s  1.6~2.4s  ← 打散，峰值被削平
```

本库用 ±25% 的抖动（`RetryPolicy.jitter`）。

### 2.3 非幂等操作绝不能重试

```
用户点"支付" → 模型调 charge(order_id, amount) → 网络超时
                 ↓
        你重试了 → 用户被扣了两次钱
```

这里超时**不代表失败**，可能只是响应丢了。所以：

```python
ToolPolicy(idempotent=False)   # effective_attempts() 强制返回 1
```

正确的解法是**幂等键**：调用方生成一个唯一 id，下游按 id 去重，这样重试就安全了。
本库目前只做了"不重试"，幂等键在局限清单里。

## 3. 超时：保护谁？

这是最常被误解的一点。

**超时保护的是调用方，不是被调方。**

```
Agent 线程 ──submit──▶ 工作线程 ──▶ 慢接口（跑 30 秒）
     │                      │
     └─ 0.2 秒后放弃等待 ────┘  ← 工作线程还在跑！
```

Python（以及大多数语言）**无法从外部杀死一个正在执行的线程**。所以：

- ✅ 超时让 Agent 不会挂死，用户体验有保障；
- ❌ 超时不会释放被占用的线程和下游连接。

推论：如果大量工具超时，你的线程池会被占满，后续请求开始排队。
所以超时**必须**配合熔断和队列长度监控（见局限清单第 2 条）。

想真正中断，只能：改成 `asyncio`（可取消的协程）、或者放在独立进程里（可 kill）。

## 4. 限流：用令牌桶保护下游

令牌桶的直觉模型：

```
桶容量 = burst（允许的瞬时突发）
补充速率 = rate_per_sec（长期平均 QPS 上限）
每次调用消耗 1 个令牌，桶空则拒绝
```

为什么用令牌桶而不是"每秒计数"？
因为真实流量是**突发**的。每秒 5 个请求，可能是均匀的 5 个，也可能是 1 秒内来 10 个然后安静 1 秒。
固定窗口计数会对后者误杀，令牌桶则允许 burst 范围内的突发。

**本库的取舍**：限流失败时**不阻塞等待**，而是抛 `RateLimited(retryable=True)`，
交给退避机制统一处理。好处是逻辑简单、不会在限流上再挂一个超时；
代价是重试次数会被限流消耗掉。生产环境更常见的做法是阻塞式获取令牌 + 独立超时。

## 5. 熔断：快速失败也是一种功能

### 5.1 为什么需要

下游整体挂了的时候：

```
没有熔断：每个请求都 → 连接 → 等超时(30s) → 失败
         100 个并发 = 100 个连接 + 100 个线程全部卡住 30 秒
         → 你的服务也挂了（雪崩）
```

熔断器的判断是：**既然它已经挂了，我就别再试了，直接告诉你失败。**
这看起来像"放弃"，实际上是**止损** —— 把资源省下来服务那些还能工作的请求。

### 5.2 三态状态机

```
             失败数 >= threshold
   ┌────────┐ ──────────────────▶ ┌────────┐
   │ CLOSED │                     │  OPEN  │
   │  放行   │ ◀────────────────── │ 快速失败│
   └────────┘   探测成功            └────┬───┘
        ▲                               │ 等待 recovery_timeout
        │                               ▼
        │     探测成功          ┌────────────┐
        └────────────────────── │ HALF_OPEN  │
                               │ 只放 1 个探测 │
                               └────────────┘
                                       │ 探测失败
                                       └──────▶ 回到 OPEN
```

三个细节：

1. **HALF_OPEN 只放少量探测请求**（`half_open_max_calls`）。
   如果恢复瞬间就把全部流量放开，刚活过来的下游会被立刻再打死。
2. **探测失败要重置计时器**。否则会在"打开 → 半开 → 失败 → 立刻又半开"之间高频抖动。
3. **`CircuitOpen` 的 `retryable=False` 是有意的**：
   熔断器已经判断"重试没意义"，此时再重试就违背了熔断的目的。

### 5.3 一个真实的坑：按"尝试"还是按"调用"记账？

我第一版是**每次失败尝试都上报熔断器**：

```
max_attempts=3，failure_threshold=3
一次调用失败 → 3 次尝试 → 熔断器记 3 次失败 → 打开
```

结果：**一次网络抖动就熔断了整个下游**。阈值 3 形同虚设。

改成只在**逻辑调用最终失败**时记 1 次：
一次调用再怎么重试，对熔断器来说只是"这 1 次调用失败了"。
`tests/test_executor.py::test_circuit_records_one_failure_per_logical_call` 就是防这个回归的。

## 6. 审计与指标：让问题可复盘、让效果可量化

### 6.1 审计日志要有入参，且默认脱敏

出问题时你最想知道的不是"报错了"，而是**"模型到底传了什么"**。
所以审计必须记入参。但入参里经常有敏感信息，所以必须脱敏。

两个容易漏的点：

1. **返回值也要脱敏**。工具经常把敏感字段原样回传（扣款接口返回订单号），只脱敏入参不够。
   这个 bug 是我在写示例时发现的 —— 审计里明晃晃地打着 `"order_id": "ORD-1000"`。
2. **脱敏要递归**。敏感字段可能在嵌套结构里。

### 6.2 指标要能回答四个问题

| 指标 | 说明什么 |
|---|---|
| **成功率** | 工具描述 / Schema 质量够不够 |
| **重试率** | 下游稳不稳定（突然升高 = 下游出事了） |
| **P95 延迟** | 用户会不会等太久 |
| **熔断/限流次数** | 下游挂了多久、配额够不够 |

还有一条**不变量**值得每次运行都断言：

```
实际尝试次数 = 通过校验的调用次数 + 重试次数
审计记录条数 = 实际尝试次数 + 校验失败次数
```

这两条对不上，说明你的埋点漏了或者多记了。

## 7. 可测试性驱动设计

这个库所有涉及时间的东西都支持注入：

```python
ToolExecutor(registry,
             sleeper=lambda d: sleeps.append(d),   # 退避不用真等
             clock=lambda: now[0])                 # 熔断恢复不用真等
RetryPolicy(jitter=0.5, rng=random.Random(1))      # 抖动可复现
```

**如果一段涉及时间和并发的代码没法测试，那通常是设计问题，不是测试问题。**

举两个例子：
- 想测"熔断 5 秒后恢复"，注入 clock 后瞬间完成；
- 想测"重试的退避序列是不是 0.1 / 0.2 / 0.4"，注入 sleeper 后直接断言列表。
